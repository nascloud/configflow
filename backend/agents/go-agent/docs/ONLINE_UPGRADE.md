# Agent 网页在线升级方案

目标：标准 Shell 安装的 Go Agent 在网页点击更新后完成程序升级、旧配置迁移和旧启动恢复依赖清理；保留身份、配置路径、端口与核心文件，不要求重新执行安装命令。Mihomo、MosDNS、OxiDNS 核心启动均不再依赖 Agent 或部署恢复服务。

## 流程与成功条件

1. 后端确认目标版本的架构文件、长度和 SHA-256，创建持久升级记录。
2. Agent 校验更新条件，拒绝与配置发布、恢复、其他更新并发。
3. 下载到可执行文件所在文件系统，校验完整性、架构和版本。
4. 独立更新任务备份程序、Agent 配置和将修改的系统启动文件。
5. 保留旧配置全部字段，补齐标准 systemd/OpenRC 生命周期；不解析执行任意旧命令来推断生命周期。
6. 清理旧 systemd/OpenRC 恢复服务及相关启动依赖，保留用户其他设置。更新过程不重启正在提供服务的核心；新版普通 Agent 启动只读检查部署记录并提示待处理问题。
7. 原子替换 Agent，重启对应 Agent 服务，确认版本、身份、迁移状态及认证 API。
8. 成功后确认版本；失败恢复程序和本次修改的配置及启动文件，再确认旧服务在线。
9. 状态与错误持久化，页面刷新和后台重启后仍可查询；未收到确认不能显示成功。

## 首次旧版升级

已有旧 Agent 的下载/替换逻辑无法被新后端直接修改。兼容接口继续支持旧协议，新版首次启动须自动迁移并能从旧更新器留下的备份恢复。必须分别验证旧协议过渡和新协议完整升级，不能以新安装验收替代旧版升级。下载前就发生的旧协议限制需如实返回，不得伪报升级成功。

## 保留与隔离

- 保留 ID、Token、服务器地址、Agent 端口、核心配置、规则和未知配置字段。
- 只移除 ConfigFlow 恢复依赖、对应服务文件及 OpenRC 标记区，保留用户原有 unit 中的其他设置。
- 自定义生命周期无法可靠识别时，返回具体缺失字段并恢复旧版本；这类自定义安装需人工补齐生命周期字段，不猜测任意 shell 命令。
- 更新锁覆盖共享 Agent 二进制，阻止重复更新；事务发布锁保护核心操作。
- 不在日志或网页暴露 Token、下载凭据或完整配置内容。

## Docker 边界

Docker 容器内替换二进制不能代表镜像升级。完整镜像升级需要宿主机更新通道，保留挂载、环境、端口和容器身份，并由容器外任务执行重建和回滚。没有该通道时必须明确提示镜像升级方式，不能沿用 Shell 更新按钮并显示成功。

## 验收

验证 systemd、OpenRC；Mihomo、MosDNS、OxiDNS；旧版本首次升级、新协议升级与重复点击；正确文件、下载错误、校验不符、迁移失败、新程序启动失败、更新进程中断及恢复。确认身份和核心文件不变，失败后的旧 Agent 可用，成功后可以实际发布配置。还需确认升级清理已有恢复依赖，Agent 停止时核心能够独立启动。Docker 验收按最终选定的更新范围单独执行。

## 用户实际操作与依赖

1. 先将 ConfigFlow **主服务**更新到包含本功能及 1.6.1-go 三种架构程序的镜像；网页以主服务随镜像提供的版本为准，不查询 GitHub 后自动安装未配套的版本。
2. 在 Agent 页面点击“更新”。标准 Shell 安装无需重新执行安装命令，也无需向主服务提供 SSH 权限。
3. 页面显示下载、校验、备份、迁移、替换、重启和确认阶段；刷新页面继续查询同一任务。
4. 成功必须由正确 ID 的 Agent 通过认证接口确认目标版本与迁移就绪。程序重启期间连接失败不代表升级成功或已回滚。
5. 失败显示具体阶段；完成回滚后允许重试。回滚未完成、状态未知时保留任务并阻止发布、重启、卸载和再次更新，避免覆盖恢复证据。

Shell 需要原有的 root 服务权限、可写安装目录及 systemd 或 OpenRC。systemd 使用独立 service，兼容旧版 219；OpenRC 使用其自带的 `supervise-daemon` 监督更新任务。无需安装 curl、tar、Python 或 Docker 来执行 Shell 更新；下载、SHA-256、配置处理和原子写入均由 Agent 完成。Python/Docker 仅用于本仓库的隔离验收。

Docker 本次保持镜像更新方式。检测到新版后，网页保留“更新”按钮，点击打开 Compose / Docker Run 操作指南，不调用容器内二进制升级接口。Compose 用户确认实际服务名后，可复制针对单个服务的拉取及 `up -d --no-deps` 命令；自定义项目、文件和环境参数需沿用原值。Docker Run 用户可修改并复制目标镜像的拉取命令，再按原启动参数重建容器。指南明确要求复用数据挂载、保留旧容器用于恢复，并提供刷新列表核对版本的入口；复制命令和打开指南不代表更新成功。

## 日志和恢复数据

- 后端将当前更新 ID、目标版本、时间、阶段和结果写入 Agent 记录。
- 程序目录下 `.configflow-updates/` 保存各任务独立状态文件、受权限保护的配置快照和程序备份。`current.json` 记录当前任务；旧任务不能覆盖新任务的结果。
- systemd 更新日志使用 `journalctl -u configflow-upgrade-<任务 ID 前 16 位>` 查询；OpenRC 更新日志为 `.configflow-updates/<任务 ID>.log`。
- 配置快照含认证信息，仅写入本机 0700 目录内的 0600 文件；公开状态接口不返回快照。
- 更新失败恢复原程序、配置内容、权限与所有者以及启动依赖文件。任务进程中断后由服务管理器重新拉起，依据持久记录恢复。

## 首次旧协议的明确限制

旧版 1.0.8-go / 1.1.0-go 更新器已经存在于用户机器上，首次点击时仍会先运行其旧逻辑。新版成功启动后会自动迁移，迁移失败会恢复旧程序并确认旧版心跳。后续更新才完整使用独立更新任务。

首次旧协议中，损坏到无法执行的新 ELF、旧下载器的跨文件系统 rename 问题、断电发生在旧更新器替换期间等情况，不能由尚未运行的新代码保证自动修复。此类情况不能声称“全部失败都能回滚”。此前验收使用标准路径 `/usr/local/bin/configflow-agent` 与 `/opt/configflow-agent`；自定义路径和任意 shell 生命周期命令不做未经验证的自动推断。机器断电未以真实整机断电方式验收。

## 1.6.1-go 启动行为及验证边界（2026-10-16）

普通 Agent 启动、`-check-deployments` 及弃用兼容参数 `-recover-only` 只读检查部署事务，不取得服务操作锁、不停止核心、不恢复文件；发现未完成事务时记录提示。实际部署恢复需明确执行 `-recover-and-exit`，推送期间的校验、备份、健康检查和失败回滚继续保留。成功发布后的显式手动回滚、OxiDNS 原生校验、工作目录校验及 state 数据保护也保持不变。未解决事务仍阻止后续发布和服务变更，具体命令见 [失败诊断与恢复](DEPLOYMENT.md#失败诊断与恢复)。

验收脚本已改为检查 systemd/OpenRC 升级清理旧依赖、保留无关设置，以及核心独立启动；原生及 Docker 崩溃场景改为确认启动保留事务和文件，再人工恢复。AIO 场景可分别选择 MosDNS 或 OxiDNS 与 Mihomo 组合，检查 Mihomo 配置损坏时另一个核心和两个 Agent API 仍可启动，人工恢复 Mihomo 不影响另一个核心。OxiDNS 验收需要包含该核心的最新测试镜像或对应二进制，历史双核心结果不覆盖 OxiDNS。

原生/单核心 Docker 验收默认覆盖三种核心；AIO 用 `--dns-core mosdns` 与 `--dns-core oxidns` 分别运行，不能同时启用两个默认使用 53 的 DNS 核心。在线升级验收的 OxiDNS 发布直接调用 Agent API；现有 Flask 发布 fixture 仍只覆盖 Mihomo/MosDNS，OxiDNS 不计为已验证 ConfigFlow 转换/打包链路，报告会标明该边界。

本次已在 NAS 正式部署新版 ConfigFlow 主服务，并通过主服务正式的 `upgrades.start/poll` 流程，将 systemd 原生 OxiDNS Agent 从 1.6.0-go 在线升级至 1.6.1-go。已确认旧恢复服务及关联 systemd drop-in 清理完成；Agent 可独立重启，停止 Agent 后 OxiDNS 核心仍可重启；整机 reboot 后 Agent 和核心自动启动，UDP/TCP DNS 查询正常。升级及重启前后，64 个受管文件的内容哈希和 Agent 身份哈希均保持一致。此处验证的是主服务在线升级入口及实际服务行为，不是浏览器点击验收或真实断电验收。

Go 全包测试、106 项相关 Python 测试、Linux amd64/arm64/armv7 三架构构建及前端生产构建均通过；集成脚本的 Python 语法检查通过。

本次尚未真实重跑 OpenRC、Mihomo、MosDNS 和 Docker Agent 的完整验收矩阵，OxiDNS 的上述成功路径也不代表所有升级故障与恢复场景均已重新验证。下面保留的历史结果和机器记录不扩大 1.6.1-go 的实际验证范围，旧恢复门禁测试不能用于证明新启动行为。

## 历史验证结果（2026-10-10，旧启动恢复行为）

在隔离 Linux 测试主机的独立目录、端口和临时服务验收，未替换生产 Agent 或重建生产容器。测试使用源码原样编译的旧版程序，调用实际 ConfigFlow 更新与发布接口。

| 环境 | 旧版 | Mihomo + MosDNS | 结果 |
|---|---|---|---|
| Linux / systemd 219 | 1.0.8-go（5c5f5d8） | 18 项最终完整矩阵 | 全部通过 |
| Alpine / OpenRC 0.63.2 | 1.0.8-go（5c5f5d8） | 16 项最终完整矩阵 | 全部通过 |
| Linux / systemd 219 | 1.1.0-go（98e5550） | 18 项补充兼容覆盖 | 全部通过 |

当时覆盖：首次旧版在线升级、旧配置与未知字段保留、新协议更新、HTTP 503、文件完整性不符、候选程序启动失败回滚、强制终止更新进程后的恢复、升级后实际发布配置，以及当时的恢复服务先于核心启动。最后一项行为已在 1.6.1-go 取消。systemd 还包含无法识别自定义生命周期时恢复旧程序并确认心跳的失败场景。升级期间持续检查核心进程状态并核对核心配置和规则文件未改变；发布后通过实际 HTTP/DNS 检查服务。

完整后端回归 1350 项通过、2 项跳过；补齐 Docker 更新指南后前端回归 119 项通过，包含两类核心的 Docker 更新入口、Shell 升级入口、命令复制和无效参数保护；Go 全包竞态测试通过；前端生产构建通过。真实验收结束后补充了损坏任务记录的拒绝放行保护，并通过相应 Go 竞态回归。amd64 在服务器真实运行，arm64/armv7 只验证交叉编译。没有将 API 端到端验收表述为浏览器实点验收。

[机器可读记录](ONLINE_UPGRADE_ACCEPTANCE.json) 保留各项结果及对应测试程序摘要。临时原生服务、更新任务和 OpenRC 容器已清理；日志和报告留在独立验收目录。用户网页要在主服务镜像包含本次改动后才获得新流程。Docker Run 自动读取旧容器参数、重建和回滚尚未实现；本次 Docker 范围仅为更新指南。
